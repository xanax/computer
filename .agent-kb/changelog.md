2026-10-07 — provider-retry-policy — Retried every outbound provider call instead of only 429/5xx: one policy module (`cptr/utils/retry.py`) consulted by the three streaming transports (which drive their own loop, because replaying a request whose text is already on screen would duplicate it — an `emitted` flag guards that), by `chat_completion` (which had **no** retry at all, so a transient 5xx silently dropped every title/summary call), and by image generate/edit plus STT/TTS. 2026-10-04 — sqlite-write-lock — A turn in chat `7ceb3817` died mid-way with `sqlite3.OperationalError: database is locked` out of `ChatMessage.update`, discarding its text and 166 tool calls, and it read like a provider failure when nothing external was involved. SQLite grants one writer at a time and a turn commits its entire `output` JSON blob (1,292,023 bytes for the failing row, up to 5.9MB here) in a single transaction, while `get_engine()` set only `journal_mode=WAL` and left `busy_timeout` at SQLite's 5000ms default — so any save slower than 5s failed every turn saving beside it. A real log's save histogram (7596 saves, median 17ms, **max 40.17s**, 9 over budget) and the production failure's 5.886s wait name the mechanism; the fix is `connect_args={"timeout": 60}` plus a per-connection `connect` event hook (`busy_timeout`, `synchronous=NORMAL`) and `?timeout=` on the Alembic URL, all at the single `get_engine()` choke point (B-024).
